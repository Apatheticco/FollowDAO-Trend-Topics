# 📈 周复盘 — 效果评估流程（v2.8.3）

> **触发**：用户说「跑周复盘 / 效果复盘 / 这周效果怎么样」，或 AUTO 周任务（如每周一首扫后追加跑）。
> **数据源**：`~/.trend-scout/snapshots.tsv`（每轮 B0 快照）+ `~/.trend-scout/actions.tsv`（我方写操作日志）——两者都由执行卡 §0「收尾双留档」逐轮积累；API 只给当前态，**没有这两份文件本流程无法运行**。

## 流程

1. **拉最新 B0**（`list_trending_topics` 近 7 天全状态）作"当前终态"。
2. **读两份留档**：`grep` 近 7 天行；按 id 关联 快照序列（status 变迁）× actions（哪些是我做的）。
3. **算四组指标**（能算多少算多少，数据不足的标 `n/a` 并注明原因，不硬编）：

### 第 0 层：自动化收敛（v2.9.70 —— 北极星：用户点名/周 → 0）
> 完全自动化的判据不是"指标好看"，而是**系统不再依赖用户当质量闸**。本层趋零并稳住 2~3 周，才有资格把触发从人工切到定时任务。
| 指标 | 算法 | 读法 |
|------|------|------|
| **用户点名数** | `log-action.sh stats 7` 中 `reason_code=用户点名` 的行数（跨全部 action），**按错误类型分列**（归因/漏跑/口径/判留…） | **北极星**。与 v2.9.49 点名纠正率同源，看绝对数+类型迁移。⚠️ ~~`grep "★用户点名"`~~ **口径已废（v2.9.71）**：它只数带 ★ 的 note 行，实测漏掉散在 update/rulefix/cull/create/merge 里的同类行——全历史 7 vs 真实 48，**北极星本身少数了 6 倍** |
| 自审抓到数 | `grep "★自审\|★修正\|★口径拦截\|★②c抓反转"` 中当轮实际修正项 | 与点名数此消彼长＝复审在替用户接活；两者同降要查是不是没在干活 |
| 补跑捞回数 | `grep "★补跑捞回"` | >0＝清单执行仍有洞（checklist.sh verify 应压到 0） |
| 复审员挑战/成立数 | 独立复审员（AUTO 0b）当周挑战数及其中确实改/撤的 | 成立数高＝六查漏网多，把成立案例归类回填硬闸 |

### 第 0.5 层：决策归因分布（v2.9.71 —— 每一次建/撤/改都要能被聚合）

> **为什么加这层**：actions.tsv 记了 1210 行归因，却**一条分布都算不出来**——归因写在自由文本第 4 列，而 `action` 列被当自由标签用出了 **203 种取值**（撤题散在 15 个标签、改题散在 19 个）。记录 ≠ 可学习，**能聚合才是**。
> **执行载体＝`~/.trend-scout/log-action.sh`**（与 checklist.sh / log-snapshot.sh 同级强制）：6 列 `run_ts｜action｜id｜reason_code｜备注｜标题变更`，action 与 reason_code **双枚举校验，不在表内直接拒写**；`update` 不带「旧标题→新标题」拒写（旧格式从不留存标题变更，改题记录等于没有）。历史 1210 行由 `backfill-reasons.awk` 回填成派生只读视图 `actions-backfilled.tsv`（未分类率 18.4%）。

| 指标 | 算法 | 读法 |
|------|------|------|
| **撤题归因 TOP** | `log-action.sh stats 7` 的 cull 段 | **系统在持续生产哪一类垃圾**。某类连续 2 周居首 → 该前置成预过滤形态闸，而不是每轮人工清 |
| **建题支撑构成** | 同上 create 段 | `有诱因-多源` 占比越高越健康；`纯行情-A定则`/`meme豁免` 是合规兜底不是主力，占比冲高＝当周真事件少或诱因没查够 |
| **改题类型** | 同上 update 段 + 标题变更流水 | `改数字-定稿` 是排班正常代谢；`改归因`/`改口径-时段` 高＝建题时口径没锁死，回头返工 |
| **未分类率** | `awk '$4=="未分类"' actions-backfilled.tsv` | >20% ＝ 枚举表跟不上真实决策类型，补枚举（**禁止塞自由文本绕过**） |

**基线（2026-08-28 首次全量回填，1215 行）**：
- 撤题 137 条可分类 → **`A闸不过-灌水` 56 条（41%）**，是第二名的 4 倍；其余：重复 23（同标的13＋碎片10）、事实错误 20（数字13＋定义7）、反转错向 11、归因问题 12（借源造因9＋反向3）、缺价格腿 7、疑问句 6
- 建题 87 条可分类 → 有诱因-多源 39、板块聚合 19、承接兑现 11、预告题 7、meme豁免 7、单源待核 4
- **第一条可执行结论**：`A闸不过-灌水` 的题形态高度同质——KOL 观点（何一/Ansem/CryptoQuant）、产品公告（roadmap/AMA/TGE）、vanity 指标（TVL破X亿/持币X万/mNAV）、融资无标的。**每轮人工清同一类 = 0a.5 预过滤拦不住**，应升级成形态特征闸。

**升级规则（自我学习闭环）**：同一错误类型被用户点名**第 2 次** → 当场自动起草规则补丁（写成 diff 存 `~/.trend-scout/pending-patches/`，**不落 SKILL**），周报置顶等用户拍板——学习从"挨打后补 LESSONS"变成"有方向的收敛"。

**⚠️ 毕业指标换轨（v2.9.77 —— 防"假性归零"）**：北极星（用户点名数）**只在监督期有效**——它依赖用户在看；真托管后用户不看了，点名自然为 0，**指标失效而非达标**。两段判据写死：
- **切换前**（现阶段）：用点名数/周判收敛，趋零稳 2~3 周才有切 cron 资格（不变）。
- **切换后**：北极星**必须换轨**为不依赖用户在场的信号——① 团队打回率（我上线的题被 console 侧 →3 的比例，快照可算）② 复审员挑战成立率（台账可算）③ 返工率（≤8h 内自改比例）④ 终局用 dev 的 PV/heat 字段（工单在册）。**换轨动作本身入切换 checklist**：切 cron 那周的周报必须同时报两套指标各一期，确认新轨能算再停旧轨。拿"托管后点名为 0"当毕业证 ＝ 拿没人监考当满分。

### 第一层：编辑采纳（团队 = 评委）
| 指标 | 算法 | 健康线 |
|------|------|--------|
| 采纳率 | 我 create（actions=create）且后续快照/终态出现 status=0 的 ÷ 我 create 总数 | 越高越好；持续 <30% 说明我的闸和团队口径脱节 |
| 打回率 | 我 create 后被 →3（非我 cull）的比例 | 越低越好 |
| 误撤率 | 我 cull（→3）的 id 后来又回到 0/2 的比例 | ≈0 为健康；>10% 说明复审杀良 |
| 合并存活 | merge-keep 的 id 在终态仍 status=0 的比例 | 高=打包质量好 |
| **点名纠正率**（v2.9.49 新增） | 当周**用户点名纠正次数** ÷ 当周处置的系统题总数（cull＋hide＋merge-hide＋factfix-hide＋publish＋update 去重计数） | 越低越好；**先立基线看趋势，不设绝对线**。基线：08-10~08-16 为 **7／约 180 ≈ 3.9%** |

> **为什么必须有这一条（v2.9.49 — 08-18 用户拍板）**：上面四个指标的**分母全是「我 create 的题」**，而复审侧（我 cull／改／推上线的系统题）质量**没有任何指标在测**。
> 08-10~08-16 那周采纳率 93.8%、打回 0%、误撤 0% 三项满分，但**同期 7 次用户点名纠正全部落在复审侧**——指标漂亮和短板暴露同时发生，说明指标体系整个偏了一侧。
> **计数口径**：① 只计「用户明确指出某条题/某个判断有问题」，不计用户提问、要求或方向性建议；② 一次对话里针对同一条题的多轮追问算 1 次；③ 我自查发现并修正的**不计入分子**，但应在定性段单列（自查率是反向健康信号）。
> **读法**：分子降 = 判得准了；分母降而分子不降 = 我在少干活而不是干得好，**要一起看**。


### 第二层：工艺质量
| 指标 | 算法 |
|------|------|
| 返工率 | 我 create 的 id 在 ≤8h 内又有我 update（改价/改题）的比例 |
| 时效领先 | 抽查本周 P0/P1：催化 published_ts → create run_ts 时滞；是否早于系统碎片 |
| 池子卫生 | 每轮检测的碎片/重复数按天列，看趋势是否收敛 |
| 覆盖率 | 大行情日（\|BTC\|>5% 或板块>3%）当天，线上是否有过闸话题（人工抽查 B0）|

### 第三层：定性
- LESSONS 版本表本周新增条数（规则被顶回的频率，理想趋稀）
- 干轮轮数占比（如实报即可，不设好坏——行情清淡就该多干轮）

4. **规则卫生（v2.9.30 新增固定步骤——v2.9.24「满 30 天反例沉 LESSONS」约定的唯一触发器）**：检查 SKILL 中 v2.9.15 起各规则的反例护栏是否已满 30 天（按版本行日期算），满则压成一句指针、完整反例沉入 LESSONS 对应版本行；同时报 SKILL 当前行数 vs 梳理基线 207。
5. **规则全量 review + 梳理（v2.9.74 —— 08-29 用户定「每周 review 最后加一项：review 所有规则，再梳理一下」，周报固定收尾项）**：
   - **通读不抽查**：把 SKILL.md 执行卡逐条过一遍（含 references 索引指到的判定节），每条规则问四个问题：
     ① **过期了吗**——规则针对的工具/接口/参数/排班还存在吗（先例：`CLUSD` 废弃、旧钟点判据作废）；本周实测有没有证据说它描述的世界变了；
     ② **矛盾了吗**——与本周新立的版本打架吗；**同主题规则是否散落多点各自演化**（违反 v2.8.2「单点归拢」架构约定，A 闸/去重树/status 口径各只准有一节）；
     ③ **被实践推翻了吗**——本周的用户点名/复审员成立挑战/回扫结论，有没有证明某条规则的**动作指向错了**（先例：v2.9.68「查因果句式」对利好配跌类指向错位 → v2.9.72 收窄）。判据不是"规则被违反过"而是"照着做也会错"；
     ④ **冗余了吗**——两条规则在管同一件事、或某条已被更强的后续版本完全覆盖 → 合并成一条留指针。
   - **行数体检**：SKILL 当前行数 vs 基线 207；**超 2 倍触发强制压缩提案**（膨胀本身就是执行负担——每轮加载的规则越长，单条被调用的概率越低，v2.9.72 LESSONS「规则知道 ≠ 执行时会调用」正是行数病的症状）。
   - **产出＝梳理提案**：合并/压缩/沉降/废止四类清单，逐条附证据与拟改写法，**不自动改 SKILL**——提案入周报置顶，用户拍板后当场执行并入 LESSONS 版本行。若本周四问全空，如实报"规则集本周无梳理项"，不硬凑。
6. **输出**：表格化周报（v2.7.9）——四组指标表 + 逐条明细（我建的每条：id/标题/终态/被谁改）+ 规则卫生结果 + **规则梳理提案（第 5 步产出，置顶）** + 一句话结论 + 下周改进项（若有指标越线，提出具体规则调整建议**但不自动改 SKILL**，等用户拍板）。
